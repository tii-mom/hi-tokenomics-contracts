HI 代币发行与合约系统最终方案

本文件描述 HI 发行后的分配逻辑、增长引擎、价格解锁、团队释放、生态奖励、500万 HI 活动奖励和合约之间的关联。此版本按最新确认：增长引擎与活动奖励均以 USDT 价格达标为解锁条件，团队按 0.1 / 0.5 / 1 / 5 USDT 四档释放。

总量 10,000,000,000 HI 7 合约架构 GrowthEngine 替代 PublicSale Mainnet 仍未授权部署

发行原则

  • HI 总量固定为 10,000,000,000 HI。
  • 部署时一次性 mint 全部供应并完成分配。
  • 分配完成后 JettonMinter admin 弃权，后续不能增发。
  • 不设计税费、黑名单、冻结、强制转账或管理员转走用户余额能力。
  • 持币业务合约预留受限迁移能力：目标地址必须先由管理员加入 allowlist，再由两个指定迁移钱包之一发起，且只能迁移未承诺 HI。
  • 项目基金、流动性、投资及早期直接打入固定钱包，不开发额外 vault。

价格解锁原则

  • 增长引擎、团队释放、500万 HI 活动奖励均以 USDT/HI 价格达标为准。
  • 忽略 TON/HI 换算关系，TON 只作为购买支付资产。
  • 价格由 PriceOracle 上报并确认。
  • 测试网时间锁可用 30 seconds；主网使用 86400 seconds。

合约间受限迁移机制

每个持有 HI 的业务合约都需要预留“合约到合约”的受限迁移能力，用于应对合约升级、业务迁移或异常恢复。这个能力不是管理员提现通道，不能把 HI 转到普通钱包。当前 V1 采用“管理员目标 allowlist + 双迁移权限钱包 + 单个已选择目标”的方式：管理员先把目标地址加入对应合约的迁移 allowlist，两个迁移钱包之一才能选择该目标并迁移未承诺 HI。

规则说明
适用合约GrowthEngine、TeamVestingVault、CampaignWinnerVault、MerkleRewardVault。
发起方只能是部署前或初始化时写入的两个指定迁移权限钱包之一，例如两个迁移多签，或一个项目多签加一个强隔离备份多签。
允许接收方只能是管理员先加入迁移 allowlist、再由迁移钱包选定的目标地址；业务口径要求它是新版 GrowthEngine、新版奖励 vault、新版团队 vault 等目标合约。
禁止接收方未加入 allowlist 的地址、管理员个人钱包、项目方个人钱包、普通用户钱包。
可迁移额度只能迁移未承诺、未售出、未注册、未发布 batch、未归属用户的余额。团队 12% 在 TeamVestingVault 中全部视为已承诺，不能迁移。
不可迁移额度用户已购买未领取额度、winner 已注册额度、Merkle batch 已发布未领取额度、全部团队释放额度。
权限建议使用两个固定迁移权限钱包，任意一个可发起迁移；主网建议两个钱包都使用多签。管理员 allowlist 操作需要在部署/运维记录中公开。
审计目标证明未 allowlist 的 target 不能被选择，两个迁移权限钱包不能迁移用户权益，只能迁移未承诺 HI。

发行后分配流程

1. 部署 JettonMinter设置 HI metadata，admin 暂时为部署/管理员钱包。
2. 部署功能合约部署 GrowthEngine、PriceOracle、TeamVestingVault、CampaignWinnerVault、MerkleRewardVault。
3. 注入 Jetton Wallet为 GrowthEngine、TeamVestingVault、CampaignWinnerVault、MerkleRewardVault 设置对应 Jetton Wallet。
4. 一次性分配mint 全量 100 亿 HI，并按 50/20/12/10/5/3 分配。
5. 配置 Oracle 目标PriceOracle 同步增长解锁、团队解锁和活动奖励需要的价格 level。
6. 弃权 Mint 权限分配完成后 drop minter admin，证明不能再增发。
7. 运营阶段用户购买、claim；管理员只负责上报价格和创建 Merkle batch。
8. 主网审计主网部署前完成审计/独立 review、真实地址确认和最终授权。

4. PriceOracle

USDT only Growth level 0-10 Team level 0-4

PriceOracle 只处理 USDT/HI 价格达标，不再处理 TON/HI 换算。它负责两类价格确认：增长解锁 level 和团队释放 level。

Level 类型范围用途同步目标
growthConfirmedLevel0-10GrowthEngine、CampaignWinnerVault、需要价格达标的 Merkle batchGrowthEngine / CampaignWinnerVault / MerkleRewardVault
teamConfirmedLevel0-4团队 12% 分 4 档释放TeamVestingVault

管理员只能上报价格和触发确认；门槛写死在合约中，确认 level 只能递增，不能跳级，不能回退。测试网 delay 为 30 秒，主网 delay 为 86400 秒。

6. CampaignWinnerVault

500万 HI 活动大奖池 与 GrowthEngine 对齐

CampaignWinnerVault 承载 500万 HI 达成大奖池。它需要与 GrowthEngine 的 growthConfirmedLevel 对齐，所有释放都以 USDT 价格达标后的 growth level 为准。

项目规则
资金规模400,000,000 HI，从生态奖励池划拨
最大 winner80
每个 winner5,000,000 HI
注册admin 注册，合约不做 Telegram、邀请、风控判断
entryLevel注册时记录当前 growthConfirmedLevel
释放与 GrowthEngine 一致：若在 growthConfirmedLevel = 0 注册，注册后可领取 5%；level 1-9 每轮释放 10%；level 10 最后释放 5%。
晚注册规则如果 winner 在第 N 轮已确认后注册，不领取 level 0 和历史 1-N 轮，只能从下一轮到 level 10 继续领取。
历史补发不补历史

7. MerkleRewardVault

20% ecosystem allocation 500,000,000 HI campaign budget Batch-level price gate

MerkleRewardVault 承载生态奖励、当前项目 500万 HI 活动奖励、红包奖励等奖励。链下系统决定谁能领和能领多少，链上只验证 Merkle proof、防重复领取和发币。

这里的统一红包奖励从 1,600,000,000 HI MerkleRewardVault 总池中占用额度，不是额外增发或额外预算。当前 500万 HI 活动停用独立普惠抽奖，poolType=2 链上 cap 为 0 HI；红包奖励子上限调整为 100,000,000 HI，生态/运营奖励使用剩余额度。

项目规则
总资金1,600,000,000 HI，生态总额中的另外 400,000,000 HI 独立进入 CampaignWinnerVault
当前项目 500万 HI 活动500,000,000 HI 从生态奖励中划拨
当前红包子上限当前活动停用独立普惠抽奖；统一红包奖励最多 100,000,000 HI，计入 1,600,000,000 HI MerkleRewardVault 总池。
批次字段batchId、merkleRoot、totalHi、metadataHash、poolType、requiredGrowthLevel
价格门槛requiredGrowthLevel = 0 表示无需价格门槛；1-10 表示必须达到对应 growth level 后才能领取
防重复同一 batchId + address 只能领取一次
失败回滚Jetton transfer bounce 后恢复 claimed 状态和 claimedHi
受限迁移只能由两个指定权限钱包之一迁移未发布 batch、未承诺给用户的余额到管理员 allowlist 后的目标地址。

因为你确认“项目里的 500万代币奖励合约都需要 USDT 达标”，所以 MerkleRewardVault 必须增加 batch 级别的 requiredGrowthLevel，否则价格门槛只能靠后端控制，链上不够透明。

测试与部署要求

  • 本地必须通过 acton fmt --check、acton build、wrapper 生成、acton test、acton check。
  • 测试网使用 HI_ORACLE_CONFIRMATION_DELAY=30 跑完整流程。
  • 测试网必须覆盖 GrowthEngine 买入、晚买不补、claim、TeamVesting 四档释放、CampaignWinner、Merkle batch 价格门槛、GrowthEngine close/sweep。
  • 主网部署包必须恢复 HI_ORACLE_CONFIRMATION_DELAY=86400。
  • 主网部署前必须完成外部审计或独立代码 review。
